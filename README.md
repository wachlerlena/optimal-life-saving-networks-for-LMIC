# Vietnam Stroke-Care Accessibility & Road-Network Resilience

Code for the thesis analysis of geographic access to stroke care in Vietnam and
the resilience of that access to road-network disruption.

The project has two halves that share the same road graph and snapping logic:

1. **An analysis pipeline** (`analysis/`) that computes demand-weighted edge
   centrality, simulates disruption scenarios, measures the resulting loss of
   accessibility, and runs a reinforcement optimisation.
2. **Interactive Folium maps** (`build_population_map.py`, `build_combined_map.py`)
   that visualise the population, hospitals, routing, and the analysis outputs as
   self-contained HTML.

---

## Methodology overview

| Step | What it does | Module |
|------|--------------|--------|
| 1–2  | Build the road graph from OSM, snap population & hospitals to it, route to nearest stroke centre (300 km hard cap) | `build_population_map.py`, `analysis/data_loaders.py` |
| 3    | **DWEBC** — Demand-Weighted Edge Betweenness Centrality: weight each edge by the household demand that routes over it | `analysis/dwebc.py`, `analysis/run_dwebc.py` |
| 4    | **Disruption scenarios** — remove the top 1% / 5% / 10% of edges by C(e) (Scenarios A / B / C) | `analysis/disruption.py` |
| 5    | **Accessibility metrics** — travel-time and isochrone-catchment loss per scenario, tier, and region | `analysis/metrics.py`, `analysis/run_metrics.py` |
| 6    | **Reinforcement optimisation** — greedy "which edges to protect" vs. a random baseline, under Scenario C | `analysis/run_optimisation.py` |

Two facility **tiers** are tracked throughout: `any` centre (thrombolysis-capable)
and `comprehensive` (thrombectomy-capable). Results are also stratified by region
(North ≥ 18°N, Central 14–18°N, South < 14°N).

## Setup

Requires **Python 3.11** (results were produced with 3.11.9).

```bash
# from the project root
python -m venv .venv

# Windows
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
# macOS / Linux
./.venv/bin/python -m pip install -r requirements.txt
```

Dependencies (pinned in `requirements.txt`): networkx, numpy, pandas, scipy,
matplotlib, folium.

## Data

The input data is **not** included in this repository. Place the following files
under `Data_vietnam/` in this exact layout (the paths are the defaults in
`analysis/config.py` and the map builders' `--` arguments):

```
Data_vietnam/
├── population.pkl                       # population centroids + household_count
├── road_osm_preprocessed.geojson        # OSM road network
├── stroke-facs-100-en.csv               # facility tier flags (specialized_equipment)
└── existing_hospitals_100/
    ├── all_hospitals.pkl                # hospital locations + IDs
    └── distances_osm_max_300km.pkl      # OPTIONAL — see note below
```

> **`distances_osm_max_300km.pkl` is optional and is *not* generated by this
> repo.** It is a precomputed pop→hospital distance table from the upstream
> Step 2 distance-matrix build. The maps still build without it — they fall back
> to the network distances computed at run time; the file only adds the
> precomputed distances for the selected hospital pair.

> If your data lives elsewhere, point each script at it with the corresponding
> `--population`, `--hospitals`, `--roads-geojson`, etc. arguments rather than
> moving files.

All analysis outputs are written to `analysis/outputs/` (created automatically).
The first run parses the GeoJSON and snaps points; intermediate artifacts are
cached to `analysis/outputs/cache/`, so later steps reuse them. Pass
`--force-rebuild` to any step to ignore the caches.

## Running the analysis pipeline

Run from the project root, in order. Each step reads the previous step's outputs
from `analysis/outputs/`.

```bash
# Step 3 — demand-weighted edge centrality (the slow one; full ~406k-population run)
# A single super-source Dijkstra over the road graph, then one shortest-path-tree
# walk per population row to accumulate C(e). NOT one Dijkstra per population point.
python -m analysis.run_dwebc
#   → edge_centrality.pkl, pop_assignment.pkl, unreachable.pkl, dwebc_summary.txt

# Steps 4–5 — disruption scenarios + accessibility metrics
python -m analysis.run_metrics
#   → travel_times_wide.pkl, tt_summary.csv, catchment.csv,
#     catchment_deltas.csv, tt_deltas.csv, metrics_summary.txt

# Step 6 — reinforcement optimisation
python -m analysis.run_optimisation
#   → optimisation_results.csv, optimisation_regional.csv,
#     optimisation_random_runs.csv, optimisation_fine_curve.csv,
#     optimisation_summary.txt, optimisation_optimalK.txt

# Thesis figures (PNGs → analysis/outputs/figures/)
python -m analysis.make_plots
```

**Quick check that the pipeline runs end-to-end** (not a faster path to results):

```bash
python -m analysis.run_dwebc --sample 5000        # random 5k population rows
python -m analysis.run_dwebc --min-lat 21         # northern band only
```

These only shrink the per-population path-walk; the one-time graph build, the
point snapping, and the super-source Dijkstra still run in full. Use them to
confirm the code executes without errors on your machine, not to skip the cost.

## Building the maps

All map builders read from `Data_vietnam/` and (for the combined map) from
`analysis/outputs/`. The generated HTML files are large and are **not** committed —
rebuild them locally.

```bash
# Population / hospital / routing map only
python build_population_map.py
#   → population_map.html

# OPTIONAL — standalone critical-edges-only map (needs Step 3 output).
# The same critical-edge tiers + legend already appear in the combined map
# below; this just renders them on their own, without the population/routing/
# explorer layers. Skip it unless you specifically want that stripped-down view.
python -m analysis.build_critical_edge_map
#   → critical_edges_map.html
```

> Note: `analysis/build_critical_edge_map.py` is **not** optional as a file — the
> combined map imports its `add_critical_edge_layers` / `add_legend` functions.
> Only the standalone `critical_edges_map.html` output above is optional.

### Combined map (population + analysis overlays + reinforcement explorer)

The combined map embeds the reinforcement explorer, which needs a precomputed
JSON. Build it once after Step 3:

```bash
python -m analysis.reinforcement_explorer
#   → analysis/outputs/reinforcement_explorer.json

python build_combined_map.py
#   → combined_map.html
```

`build_combined_map.py` expects `edge_centrality.pkl` (Step 3),
`travel_times_wide.pkl` (Step 5), and `reinforcement_explorer.json` to already
exist in `analysis/outputs/`.

### Serving for the browser

A small embedded sample renders fine by opening the HTML directly. For the full
map, build with `--server-mode` (splits heavy route/heatmap data into a sibling
`data/` folder loaded on demand) and serve it over HTTP — `fetch()` of the data
files will not work from a `file://` URL:

```bash
python build_combined_map.py --server-mode --output serve_combined/combined_map.html
cd serve_combined
python -m http.server 8000
# open http://localhost:8000/combined_map.html
```

#### Sample size / performance

Rendering every population point will freeze the browser. Control the sample with:

- `--max-marker-points` (default 1000) — clickable, route-drawing population markers.
- `--scenario-sample-size` (default 1000) — Δ-travel scenario dots (cheap; can be larger).
- `--min-lat` / `--max-lat` — restrict to a latitude band for faster testing.

## Notes on reproducibility

- Population subsampling uses a fixed seed (`random_state=0`), so subset runs
  and figures are reproducible.
- Correctness was validated with the `--sample` / `--min-lat` flags against the
  full run before producing final results.
- The large `*.html` maps and the `analysis/outputs/` artifacts are reproducible
  from the code and the input data, so they are excluded from version control.
